# 项目版本路线图

## 1. 路线图目的

本文档用于保存第一代之后的功能和技术方向，避免因为首版聚焦而遗忘后续需求。路线图不是当前版本的承诺，具体排期需要结合内容数量、访问量、维护成本和真实使用反馈调整。

## 2. 版本边界

### 第一代：可发布的个人技术博客

目标是让作者可以稳定地写作和发布，让读者可以顺畅地浏览和阅读。

包含：

- Astro 公开博客站点
- 独立文章发布后台
- 单作者登录
- Markdown 编辑、预览、草稿和发布
- 文章、专题、项目和记录内容模型
- 首页动态视觉效果
- 分类、标签、搜索、RSS 和 SEO
- Git commit、自动构建和部署
- 基础发布状态和失败反馈

不包含：

- 多作者协作
- 评论和社区
- 复杂数据分析
- 社交平台自动发文
- 在线代码执行

当前落地状态：公开站点、独立后台界面和 FastAPI + SQLite 接口已经建立。后台目前使用本地演示数据，API 已具备文章增删改查和草稿/发布状态字段；真实登录、后台联调、Git commit 自动提交和部署仍属于第一代后续工作。

### 第二代：内容运营与发布可靠性

触发条件：文章数量增长，开始频繁更新，单纯依赖 Git 和基础后台难以管理内容。

候选能力：

- 文章版本历史和可视化回滚
- 定时发布和撤回
- 发布前检查清单
- 后台操作日志
- 图片素材库和压缩处理
- 内容搜索统计
- 阅读量和来源统计
- 邮件订阅
- 自动生成摘要、标签和分享文案

### 第三代：互动与知识服务

触发条件：有稳定读者，希望形成反馈和持续订阅关系。

候选能力：

- 评论、留言和审核机制
- Newsletter
- 文章收藏和阅读进度
- 读者反馈面板
- 文章问答或知识库检索
- 相关内容推荐
- 多语言内容

### 第四代：工程化与实验能力

触发条件：项目内容变多，或者需要把博客作为技术实验平台。

候选能力：

- 在线代码示例
- 可执行 Demo 和沙箱
- WebAssembly 或浏览器端实验
- PWA 和离线阅读
- 全文向量搜索
- 内容知识图谱
- 多站点和主题系统
- 更完整的可观测性和性能分析

## 3. 技术留存清单

| 方向 | 当前状态 | 后续价值 | 进入条件 |
| --- | --- | --- | --- |
| 评论与审核 | 暂缓 | 获取读者反馈 | 有稳定访问和评论需求 |
| 邮件订阅 | 暂缓 | 建立长期触达渠道 | 有持续更新的内容频率 |
| 数据分析 | 暂缓 | 了解内容表现 | 访问量达到可分析规模 |
| 定时发布 | 暂缓 | 管理内容节奏 | 需要批量准备内容 |
| 版本回滚 | 保留接口 | 降低发布风险 | 发布频率或改动规模增加 |
| 多作者权限 | 暂缓 | 支持协作写作 | 出现其他内容贡献者 |
| 对象存储/CDN | 暂缓 | 优化图片和媒体 | 媒体资源显著增长 |
| 社交平台分发 | 暂缓 | 扩大内容触达 | 明确目标平台和账号 |
| 在线代码执行 | 暂缓 | 提高技术内容可体验性 | 有隔离执行环境和安全预算 |
| AI 内容辅助 | 暂缓 | 提高整理和发布效率 | 内容字段稳定且有明确边界 |
| 向量搜索 | 暂缓 | 支持语义检索 | 内容规模超过关键词搜索体验 |
| PWA/离线阅读 | 暂缓 | 改善移动端阅读 | 移动端使用比例明显增长 |

## 4. 决策记录

- 第一代采用 Astro 作为公开站点，优先静态生成和阅读性能。
- 第一代采用独立发布后台，不把作者编辑能力暴露在公开站点中。
- 第一代后台只支持单作者，避免过早引入复杂权限模型。
- 发布流程以 Git commit 为版本边界，保留追踪和回滚能力。
- 后续功能先记录触发条件，再根据真实需求实现，避免为了堆功能而增加维护成本。

## 5. 每次版本更新维护规则

每次新增或推迟功能时，需要同步更新：

1. 本路线图中的版本边界或技术留存清单。
2. [BLOG_DESIGN_REQUIREMENTS.md](BLOG_DESIGN_REQUIREMENTS.md) 中对应的验收标准。
3. 根目录 [README.md](../README.md) 中的当前进展和实现过程。
